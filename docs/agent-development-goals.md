# Bloomer 设备端开发目标

更新日期：2026-10-16  
适用项目：Bloomer 设备端采集服务（Agent）

本文件定义设备端的功能、技术方案与验收要求。看板作为独立项目消费设备端接口，界面实现不在本文范围内。仓库组织与目录约定见[仓库结构文档](repository-structure.md)。

## 1. 产品目标

在运行 Darkbloom 的设备上持续采集账户收益，保存本地历史，并通过 Tailscale 向独立看板提供查询接口。关闭看板不影响设备端采集；设备休眠、关机或采集服务停止会中断采集。

设备端是无须日常图形界面的后台服务。官方凭证留在设备上；看板通过自己的访问凭证查询设备端服务。

本次已明确的开发目标是收益采集、历史保存、恢复同步、数据清理及供看板使用的接口。Provider 状态与模型清单作为只读扩展；远程控制、实时日志、资源历史、自动策略仍属于后续候选功能，不因写入本文件而自动纳入首版交付。

## 2. 已确认规则与工程约定

### 2.1 用户确认的规则

| 项目 | 规则 |
| --- | --- |
| 正常采集 | 每 60 秒请求一次，返回上限为 50 条 |
| 扩大窗口 | 按记录 ID 去重后，如果本次窗口内新增条数恰好等于请求上限，则提高条数重新请求 |
| 默认窗口 | 每轮都从 50 条开始；本轮扩窗不改变下一轮默认值 |
| 繁忙处理 | 不实现新记录突增检测、繁忙模式或持续提高默认条数 |
| 较长中断 | 距上次成功采集达到 **30 分钟**时，恢复同步请求最近 1000 条 |
| 正常关闭 | 保存关闭时间戳，下次启动参与恢复判断 |
| 明细保留 | 只提供最近一年的明细 |
| 物理清理 | 每周执行一次，删除超过保留期限的明细 |

### 2.2 本稿采用的工程约定

以下是为实现和验收补充的具体口径，并非新增产品功能：

- 一年按滚动 **365 天**计算，以收益记录的 `created_at` 判断是否过期；数据库统一使用 UTC。
- 扩窗阶梯采用 **50 → 100 → 300 → 1000**，只在当前轮生效。
- 首次运行或没有可信历史采集时间时，直接请求最近 1000 条。
- 每周清理按“距上次成功清理满 7 天”执行；错过后补做一次。
- 正常频率不叠加每小时拉取 1000 条的回查任务，也不先发送单独的数量探测请求。
- 保留错误重试、超时和限流处理；这些属于失败处理，不属于繁忙模式。

## 3. 设备端技术方案

| 部分 | 技术选择 | 目标 |
| --- | --- | --- |
| 服务程序 | Go | 编译发布，设备无须预装 Go 环境 |
| 数据保存 | SQLite，WAL 模式 | 本地事务、去重、索引、分页，无须单独部署数据库服务 |
| 数据库访问 | `database/sql` 与 `modernc.org/sqlite` | 数据库能力随程序交付，避免额外的 CGo 运行依赖 |
| 查询接口 | HTTP/JSON，接口版本为 `/v1` | 供看板按需查询 |
| 私网入口 | Tailscale Serve | 将本机接口提供为 tailnet 内的 HTTPS 服务 |
| 后台托管 | macOS launchd | 启动和异常退出恢复 |
| 运行日志 | 本地轮转文件 | 排错并限制磁盘占用 |

Agent 默认只监听回环地址，由 Tailscale Serve 转发；同时配置应用访问凭证。收益采集与界面查询互相独立，看板请求不触发新的官方收益请求。

后台托管先采用运行 Darkbloom 的用户对应的 LaunchAgent：用户登录后运行，注销后停止。若需要无人登录时也运行，应另行评估 LaunchDaemon 及 Darkbloom 的用户会话依赖。

## 4. 收益采集逻辑

### 4.1 数据来源和已知边界

沿用已有设备实测结果：

- 官方接口为 `GET /v1/provider/account-earnings?limit=<n>`。
- 同一响应包含账户累计汇总、余额及最近收益明细。
- 已实测返回上限为 1000 条；尚未验证游标、按时间翻页或按更新时间增量能力。
- 设备凭证不能读取已测试的官方账户设备列表接口，设备列表由产品自行维护。

实现前需复验实际部署版本的接口契约。不能凭空增加 `since`、`cursor` 等参数，也不能承诺恢复窗口之外的历史。

### 4.2 正常采集

1. 服务启动后立即安排一次采集，再按 60 秒周期执行。
2. 正常轮次从 `limit=50` 开始。
3. 使用 `(account_id, record_id)` 识别同一条收益；不能用任务 ID 或时间戳替代。
4. 对响应内部的重复 ID 去重，排除已过期记录，再判断哪些是本轮开始前尚未保存的记录。
5. 本窗口新增不足 50 条：结束请求阶段，保存有效结果。
6. 本窗口新增恰好 50 条：提高至下一档请求，再按扩窗规则判断。

账户累计数量、短期收益速率和模型变化均不作为额外扩窗条件。已有记录金额等字段发生变化时允许更新，但更新不算新增。

### 4.3 扩窗规则

```text
50 条窗口全部为新增 → 请求 100 条
100 条窗口全部为新增 → 请求 300 条
300 条窗口全部为新增 → 请求 1000 条
某个窗口新增不足该窗口上限 → 结束本轮
1000 条窗口仍全部为新增 → 结束本轮，标记可能存在历史缺口
下一正常轮 → 重新从 50 条开始
```

“新增”始终相对于**本轮开始前**的数据库判断。例如先得到 50 条新记录，再请求 100 条；如果这 100 条在本轮开始前都不存在，应算新增 100 条，而非新增 50 条。

可以先合并本轮各次响应，最后统一提交；不能因为先写入了本轮的 50 条而提前停止扩窗。多次响应中相同记录采用后取得的有效字段，按 ID 合并。

扩窗不是分页，各档请求都会重新获取最近 N 条。本轮全部请求串行执行，不与下一轮采集重叠。超过一个周期时不堆积补发任务。

达到 1000 条后不继续请求更大的数量，也不无限重复请求。窗口有已知 ID 重叠只能帮助判断覆盖情况，不能单独证明所有历史完整。

首次建立历史覆盖时，1000 条全部是新记录属于正常情况：记录覆盖起点和首次导入状态，不误报为运行期间新增的缺口。

### 4.4 写入与检查点

一次成功采集至少在同一事务中提交：

- 本轮新增和发生变化的收益记录。
- 本次有效账户汇总快照。
- 最近成功采集时间、最近同步结果及覆盖状态。

内容未变化的收益记录不重复改写。HTTP 请求成功但入库失败，不得推进成功采集时间。若扩窗中途失败，不得把未完成的本轮标记为完整成功。

采集失败后由后续周期重试；网络请求设置超时。遇到 429 时遵循服务端 `Retry-After` 等限流要求。服务进程保持运行，保留最近可用数据并对看板暴露过期状态。

## 5. 启动、中断和恢复

### 5.1 持久化时间

| 字段 | 含义 | 写入时机 |
| --- | --- | --- |
| `last_successful_sync_at` | 上次完整成功采集并入库的时间 | 每轮成功事务中 |
| `last_clean_shutdown_at` | 上次正常关闭服务的时间 | 正常退出前 |
| `last_cleanup_success_at` | 上次成功完成过期数据清理的时间 | 清理成功后 |

关闭时间戳指设备端服务退出，关闭看板不写入设备端关闭时间。

不能只依赖关闭时间戳，因为强制退出、崩溃、断电时可能没有退出回调。每次成功采集时间必须持久化；旧的关闭时间也不能掩盖关闭前已经发生的采集中断。

### 5.2 恢复判断

- **首次启动或无可信成功采集时间：**请求最近 1000 条。
- **启动时距最近成功采集不足 30 分钟：**从 50 条开始，遵循正常扩窗规则。
- **启动、断网恢复或休眠唤醒时，距最近成功采集达到 30 分钟：**本轮直接请求最近 1000 条。
- **正常关闭时间可用时：**同时计算停机时长，辅助判断和解释恢复原因；以最近成功采集时间覆盖的中断区间为主要依据。
- **恢复完成后：**下一正常轮仍从 50 条开始，不保留 1000 条作为默认值。
- **时钟异常导致时间关系不可信：**采用恢复读取，不把负时间差当成正常短间隔。

恢复结果若无法与中断前历史建立覆盖关系，则保留“可能存在缺口”状态及中断区间；后续采集成功不自动抹去既有缺口。

## 6. 数据保留与每周清理

### 6.1 查询范围

查询明细时始终应用 `created_at >= 当前 UTC 时间 - 365 天`。默认概览中的历史分组统计也遵循该范围；用户请求更早时间时，明确告知可用范围。

“官方账户累计收益”保留官方原始口径，不因本地只保存一年明细而归零或截断。界面必须区分“账户累计收益”和“最近一年已保存明细合计”。

### 6.2 物理删除

- 每 7 天执行一次过期明细删除，依据记录发生时间，而非采集时间。
- 服务启动时检查是否到期；停机错过任务时补做一次，不重复执行每个错过的周期。
- 删除成功后才更新 `last_cleanup_success_at`；失败则记录错误并安排重试。
- 清理与采集写库协调执行，必要时分批删除，避免长期阻塞。
- 已删除的过期记录若再次出现在官方响应中，直接忽略，不重新入库，也不计为新增或触发扩窗。
- 覆盖信息需要同步裁剪或标记范围，不能把已过期区间继续当作当前可查询历史。

每周物理清理意味着磁盘上可能暂时保留超过 365 天、额外不足 7 天的明细；设备离线或清理失败还可能延后。查询接口始终只提供最近 365 天。

删除会释放数据库内部可复用空间，主数据库文件不一定立即缩小。文件立即缩小不是清理验收条件；空间回收维护与备份应另行安排，不能每周默认执行一次可能阻塞的全库压缩。

本次一年保留规则明确针对收益明细。其他候选历史数据若后续启用，应在实现时单独定义保留策略，不能默认无限增长。应用运行日志按独立轮转策略管理。

## 7. 数据与接口目标

### 7.1 最小数据集合

| 数据 | 保存内容 |
| --- | --- |
| 收益明细 | 记录 ID、账户与 Provider 关联、任务 ID、模型、整数微美元金额、输入/输出 Token、发生时间 |
| 账户汇总 | 官方累计记录数、累计收益、可用余额、可提现余额及采集时间 |
| 采集检查点 | 最近成功时间、关闭时间、清理时间、错误和覆盖信息 |
| 采集健康 | 当前状态、最近错误、恢复原因及必要的汇总计数 |

账户、Provider 和模型的重复信息可通过关联表保存。金额以整数微美元存储，避免浮点误差。账户汇总快照的保存粒度在实现时限制，避免每分钟无变化也永久追加一行。

### 7.2 首版查询能力

- 健康信息：服务是否运行、最近成功采集时间、数据是否过期、最近错误和覆盖情况。
- 账户概览：账户累计、余额、最近一年已保存明细合计及各自口径。
- 收益明细：时间范围、模型筛选及游标分页。
- 收益统计：按小时、天和模型聚合，并接受明确的时区参数。

接口契约保存在共享目录，具体路径和响应结构以 OpenAPI 文档为准。查询从本地数据库读取，不因打开页面而调用官方接口。同一账户的余额和累计收益不能跨设备重复相加；单设备收益需验证可靠的 Provider 映射后再展示。

## 8. 日志与运行约束

应用日志记录启动退出、认证和网络错误、限流、数据库失败、清理失败、恢复及疑似缺口。正常成功采集采用汇总日志，避免每轮打印完整响应。

建议轮转配置为最多 14 天且总量不超过 50 MB。日志不包含官方凭证、访问令牌、完整身份数据或模型输入输出。

发布体积、常驻内存、CPU、网络和磁盘写入量必须在可运行原型上测量；此前体积和内存范围属于工程估算，不能作为已完成的性能验证。

至少记录稳定运行、网络失败恢复、1000 条导入和看板查询期间的资源表现。数据库容量按最终 schema 和索引复测，并单独计算日志、WAL、备份及维护所需空间。

## 9. 验收场景

| 场景 | 期望结果 |
| --- | --- |
| 正常返回 50 条，只有 8 条新记录 | 保存 8 条；已有记录仅在字段变化时更新；不扩窗 |
| 返回 50 条，全部为新增 | 当前轮继续请求 100 条 |
| 扩窗返回 100 条，相对本轮开始前全部为新增 | 继续请求 300 条，不能因先前 50 条已写入而停止 |
| 扩窗返回 100 条，只有 70 条为本轮新增 | 停止扩窗，按 ID 合并保存 |
| 请求 1000 条后仍全部新增 | 结束本轮，按首次导入或恢复情况记录覆盖状态；不无限请求 |
| 上一轮扩至 1000 条 | 下一正常轮仍请求 50 条 |
| API 响应内部重复、已有记录更新 | 不把重复或更新计为新增 |
| 有可信检查点，关闭 10 分钟后重启 | 立即从 50 条开始 |
| 关闭前已采集失败 25 分钟，再关闭 10 分钟 | 按至少 35 分钟采集中断处理，请求 1000 条 |
| 距上次成功采集恰好 30 分钟后恢复 | 直接请求 1000 条 |
| 崩溃退出没有关闭时间戳 | 依据持久化的成功采集时间判断 |
| 初次运行、无可信时间 | 直接请求 1000 条，记录覆盖起点 |
| 仅关闭看板 | 设备端仍按计划采集 |
| API 成功但数据库提交失败 | 不推进成功采集时间 |
| 明细超过 365 天但尚未到清理时间 | 查询不返回；周清理时物理删除 |
| 清理成功后接口再次返回过期记录 | 不重新保存，不计为新增 |
| 停机错过每周清理 | 下次运行补做一次，成功后更新时间 |
| 删除后数据库文件未立即缩小 | 不视为清理失败；核验过期记录实际已删除 |

## 10. 设备端建设顺序

1. 建立 Agent 项目、数据表、时间检查点和接口契约。
2. 实现 60 秒 / 50 条采集、单轮扩窗、事务保存及错误处理。
3. 实现 30 分钟恢复判断、关闭时间戳和周清理。
4. 完成只读查询接口、认证、后台安装和运行日志。
5. 对关键恢复与清理边界做集成验证，测量真实资源占用。
6. 再按需求选择 Provider 状态、模型清单、控制、日志和资源监控扩展。
