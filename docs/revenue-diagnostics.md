# 收益影响因素与诊断采集草案

日期：2026-10-19（Asia/Shanghai）。状态：设计建议，尚未实现；频率和留存均为建议，不改变现有采集规则。

## 目标与现状

目标是解释收益变化，识别能改善的运行条件，并验证调整是否有效。收入下降时，应回答：下降发生在哪一环、有哪些支持证据、哪些原因尚不能排除。

编写草案时的 Agent schema 2 保存收益明细、最新账户汇总、同步与维护检查点、疑似收益缺口，没有设备状态历史。后续已按收敛后的范围增加 schema 3 [设备状态采集](device-state.md)；本文其余任务生命周期、平台归因等仍为后续设计。参见 [数据库说明](database.md)与[上游契约](upstream-contract.md)。

诊断链条：

```text
设备运行 → Provider 连接并具备接单资格 → 模型可服务
         → 收到任务 → 接受/排队/执行 → 完成 → 计费 → 入账
```

每一环都可能影响收益。没有收益记录，不能直接推断没有收到任务；任务可能失败、被取消、尚未完成或尚未入账。奖励、补贴、负调整等如实际存在，应与任务收入分别分析，不能套用相同的接单链条。

上游已确认存在 `model` 为 `base_reward` 的奖励明细：它在收益接口中与普通任务收入同列，没有独立类别字段。看板据此把这类行识别为「基础奖励」，金额计入总收益，但不计入任务数与单笔平均，也不参与模型之间的比较。由于没有可靠的类别列，识别依赖 `model` 字符串；上游若新增其他奖励类型，需要同步扩展识别列表。

## 建议保存的因素

| 类别 | 建议采集字段 | 主要分析价值 | 保存方式与优先级 |
| --- | --- | --- | --- |
| 可服务与接单资格 | Provider 进程/会话、连接、心跳确认、认证结果、可接单状态及阻断原因、排空/暂停/忙碌、派单等级/评分及官方解释（能取得时） | 区分进程存活、已连接、真正可接单；还原等级变化 | 第一批；变化事件 + 定期确认 |
| 模型实际状态 | 启用/宣告模型、已加载模型、ready、加载中/失败、冷启动、内存准入失败、切换起止、排队量/并发限制 | 识别“配置了模型但无法服务”、加载空窗和容量不足 | 第一批；状态事件 + 模型快照 |
| 任务过程 | account/provider/session/job/model；收到、接受、拒绝、开始、首输出、完成、失败、取消；原因、耗时、输入输出 Token、重试与结算关联 | 区分没收到、收到但没做成、完成却没入账；解释吞吐下降 | 第一批；能取得的逐任务元数据/事件 |
| 设备资源 | 主机及推理进程 CPU、GPU/Metal 指标（可读时）、内存压力/可用内存/swap、温度、热压力/降频迹象、磁盘空间及 I/O、资源限制 | 解释内存争用、过热、磁盘不足和性能下降 | 第一批基础指标；高级传感器随后验证 |
| 运行故障与供电 | 启停/重启/崩溃/OOM、睡眠唤醒、退出原因、电源来源、低电量模式；关机/断电仅保存有证据的事实 | 定位不可服务时段与恢复成本 | 第一批；事件 |
| 网络 | 实际 Coordinator 连接状态、最后确认时间、断线/重连与原因；现有连接/请求的 DNS、连接、TLS、响应耗时与错误；接口/代理/出口变化 | 定位接单链路问题 | 第一批；连接事件 + 分钟指标；不频繁测速 |
| 平台与同模型背景 | 同模型可服务节点数量、公开请求/Token 速率、平台状态事件、可用的队列/需求指标 | 识别需求下降、供给增加与平台共同异常的线索 | 第一批公共统计；仅记录真实提供的字段 |
| 价格与结算 | 有来源的费率及生效时间、收入类别、累计汇总历史、收益首次观察时间与修正历史 | 区分任务数量、任务构成、价格变化和延迟入账 | 第一批；稀疏快照/变化事件；金额沿用整数微美元 |
| 版本与配置 | Darkbloom/系统/模型/推理引擎版本，启用模型、并发/内存限制、调度与空闲策略、代理、升级/配置变更时间，人工操作标记 | 比较升级和策略调整前后，解释自动更新后的变化 | 第一批；初始快照 + 变更事件；字段白名单 |
| 采集可信度 | 各来源最后成功/失败、数据年龄、覆盖区间、解析版本、丢弃/缺失、时钟异常 | 区分无任务、数据未更新和采集器失效 | 所有采集同步实现 |
| 成本（可选） | 实测或明确标注估算的功耗/电量、电价及生效区间 | 区分毛收入提升与净收益提升 | 后续；不把硬件额定功率当作实测耗电 |

CPU、温度和内存占用都是辅助证据。高利用率可能来自接单增加，低利用率可能只是没有任务；高温与收益下降同时发生并不能单独证明热降频。应结合热压力、实际吞吐、错误及时间先后关系判断。

## 数据源与可观测边界

已核验的本项目来源只有 `account-earnings` 收益接口。以下是公开资料中的候选来源，尚未对目标设备实测，不能视为已接入能力：

- 官方 [Provider CLI 参考](https://github.com/Layr-Labs/d-inference/blob/master/docs/provider/cli-reference.md)描述 `~/.darkbloom/daemon-state.json`，以及进程、信任结果、模型加载/内存准入状态和快照新鲜度。应优先核验结构化状态文件，再考虑日志或 CLI 输出，按安装版本处理字段差异。
- 官方[网络统计参考](https://docs.darkbloom.dev/reference/stats)描述公共 `/v1/stats`，包含网络请求/Token 时间序列、Provider 状态和按模型供给数。这些适合作为平台背景；实际响应、统计范围、缓存和时间语义仍须核验。
- 任务生命周期、派单等级/评分、拒绝原因、候选但未选中原因、按模型需求和平台队列是否可读，均待验证。官方认证等级、排行榜名次不能替代派单等级。
- 平台未向本机发送的任务，本机通常缺少其决策证据。只有本机空闲而无任务时，应记录“本地未观察到任务”，不能据此确定需求不足或平台故障。
- 本机 DNS/TLS/网络探测只能证明到特定端点的结果；Bloomer 收益 API、Darkbloom 接单连接、看板 Tailscale 通道必须分别记录，不能互相替代。
- 如本地日志有任务事件，只保存白名单元数据和安全错误分类，不保存提示词、回复、令牌或完整配置/响应。日志解析不完整必须标记覆盖度，不能把未找到失败行当作零失败。

独立于设备的低频观察有助于缩小故障范围，例如另一台设备观察平台可达性和该 Agent 可达性。但 Agent 不可达也可能是网络或进程问题，不能自动断言设备断电；本机采集器停止期间，没有外部证据就只能标记未知区间。

## 数据库组织建议

保留现有收益模型，通过新增连续编号迁移扩展，不改已应用迁移。

| 数据集合 | 建议内容 |
| --- | --- |
| 设备身份与关联历史 | 本地稳定 device_id；account/provider/session 关联、生效起止、来源和可信度；支持重装换身份及一机多 Provider |
| 当前状态 | 查询实时看板的最新值，不能替代历史 |
| 资源采样 | 分钟窗口、主机/进程资源、覆盖时长与质量；初期用有单位的明确列 |
| 状态与配置事件 | 等级、资格、连接、模型、配置、版本、休眠/重启等的变化与原因 |
| 任务与任务事件 | 任务主记录及可取得的生命周期阶段；重试区分 attempt，避免重复计算 |
| 网络/平台快照 | 来源、统计窗口、缓存生成时间、网络/模型维度及可用指标 |
| 收益观察/修正历史 | 原始收益记录关联、首次观察时间、金额或归属修正；最新记录仍供现有查询 |
| 采集覆盖与结果 | 各来源成功、失败、错误类别、缺口和解析版本 |
| 分钟/小时汇总 | 收益、各阶段任务计数、成功率、吞吐、延迟、等级/状态持续时间、有效覆盖时长 |

原始事实与分析结论分别保存。结论应带证据、规则版本、置信程度和缺失证据，避免把第一次推测永久写成根因。

## 时间、关联与质量要求

1. 所有来源记录来源发生时间（如有）、Agent 观察时间和入库时间。均使用 UTC；任务耗时优先使用单调时钟。
2. 收益 `created_at` 在当前契约中未实测明确对应接单、完成还是记账。应通过 job_id 连接任务过程，不把入账时刻设备状态直接当作执行时状态。
3. Provider 与物理设备的可靠映射尚未验证。未确认时可做账户/Provider 分析，不能生成确定的单设备收益归因。
4. 缺失、不支持、权限不足、过期、解析失败和合法零值分开保存。历史采样缺口不得自动补零，也不得无限沿用旧状态。
5. 轮询发现等级变化时，保存上次确认与本次确认时刻；无法知道精确改变时间就给出区间，不伪造事件时间。
6. 状态持续时长按有效覆盖区间计算，未知时长单列。名义等级保存原始值与含义，不做无定义的算术平均。
7. 累计请求/Token/网络计数识别重启、会话变更和归零；保存 boot/session/process 实例标识，不能把计数重置当负吞吐。
8. 保存短时异常需要事件来源或更细本地采样，分钟快照不能保证捕获分钟内发生又恢复的故障。

## 采样、留存与运行开销建议

- 本地基础资源每 15 秒采样，按分钟保存平均、峰值及有效样本数；可按实际开销调整为每分钟采样。优先保证内存压力、热压力、就绪和断线事件可追溯。
- Provider 结构化状态每 5～15 秒检查并检测变化，每分钟保存确认；字段变化在下次观察时记录，只有来源明确给出事件时刻才作为精确发生时间。
- 任务及故障优先采用事件来源；公共平台统计建议 1～5 分钟一次，尊重实际缓存、限流与数据更新频率。
- 基础分钟指标、状态/配置事件及关键任务元数据目标保留 365 天，与收益可分析窗口对齐。若任务量较大，按真实容量评估短期细事件与全年汇总的取舍，并明确哪些分析将因此失去精度。
- 可选秒级原始样本只保留 7 天；小时汇总可保留更久。聚合至少保留计数、覆盖时长、峰值/极值、错误分布与状态持续时间；延迟分位数使用可合并分布或从原始样本重算，不能平均 p95。
- 遥测独立调度、各来源独立超时/失败处理，不被收益请求超时或 429 一起阻断；收益采集仍遵循已确认的 60 秒与扩窗规则。入库通过统一写入口的短事务协调，网络与系统调用不持有写事务。
- 避免频繁测速、压测、扫描模型大文件或全量复制状态/日志。新增采集器的 CPU、内存、I/O 开销也要测量，防止监控影响接单。

容量只能先估算：每分钟一条为每设备每年 525,600 条；假设行与索引合计 200～600 字节，约 105～315 MB/年（十进制），不含任务事件、WAL、备份和日志。任务事件容量需另按实际任务数估算。最终以真实 schema、真实任务量和写入测量决定留存。

## 收益下降的分析顺序

1. 检查数据覆盖与新鲜度：是否没有采到、窗口截断、时钟异常或延迟入账。
2. 检查可服务时长：进程、连接、认证/等级、模型 ready、暂停和排空。
3. 检查接单：可服务小时收到多少任务，变化是否集中在模型、等级或会话。
4. 检查任务结果：接受、拒绝、失败、取消、超时、耗时与成功率。
5. 检查工作量与计费：单任务 Token/其他计费单位、模型构成、有效价格和调整。
6. 对齐资源、网络和变更事件，判断异常先于收益变化还是后于它。
7. 对照同模型平台背景及其他设备，保留本机、网络、账户、平台等尚不能排除的解释。

例如，“14:00–15:00 收入下降 80%”至少应能区分：

- 模型加载失败导致仅 12 分钟可服务：优先处理本地就绪问题。
- 一直 ready，但实际接单连接反复重连：优先调查接单网络及协调端连接原因。
- 收到任务数稳定，完成率下降且有 OOM：本机执行故障有直接证据。
- 完成量正常，之后出现补入账：原时段收入低可能来自结算或观察延迟。
- 本机 ready，任务显著减少，多台不同网络设备同模型也下降：平台/需求因素更可疑；没有需求或调度证据时仍不能定为平台故障。

示例均为假设，不是对当前设备的诊断。

## 用于改善收益的比较方式

重点指标包括总收入、每可服务小时收入、每可服务小时收到任务数、完成率、每任务工作量、执行速度、加载/恢复耗时和各等级持续时间。成本可得时再看单位电量收入与净收益。

比较模型或配置时，控制模型、等级、硬件、时段、软件版本及平台供需背景；升级、模型切换、代理/网络调整均留事件。不能只用“切换后一个小时收入更高”证明策略有效，也不能仅按单价最高选择模型。多次重复或有可比设备/时段的对照，才能提高判断可信度；跨设备收益必须先排除同账户重复归集。

## 建设顺序与可验收结果

1. 数据源核验：建立目标版本能力清单，确认设备身份、状态、等级定义、任务事件与时间语义。
2. 第一批持久化：接单资格/连接/等级/模型、基础资源与故障、版本配置、采集覆盖、可取得的任务事件和公共平台背景。某来源不可得时明确标记，其他来源继续采集。
3. 时间段复盘：任意收益下降区间同时显示收益、任务、可服务时长、等级、资源、网络、变更和数据缺口，结论列出支持证据及未知项。
4. 优化验证：按可服务时间归一化，做模型/配置/时段比较，积累调整前后证据，再决定是否值得自动化策略。

采集验收应包含：收益接口失败时本地遥测仍写入；模型加载失败可回看；短时断线不被状态平均掩盖；会话重置不产生负计数；采集器离线显示未知；收益延迟入账不误配执行状态；等级变化能追溯来源与观测区间；升级新增迁移不损伤现有收益查询。
