# Agent 数据库、迁移与恢复

当前数据库 schema 为 **10**；迁移位于 `apps/agent/migrations`，编译时嵌入程序。schema 1 是 P1 的基础表，schema 2 增加采集与维护的进程级检查点和清理索引，schema 3 增加设备身份和设备状态历史，schema 4 的旧路由列仅保留为升级历史；schema 5 增加本机任务标志、设备最新收益、空闲判定与已确认设备身份关联。schema 6 增加授权心跳、会话 ID、告警规则状态、最近 50 条告警记录与持久化发送队列。schema 7 将设备 telemetry 改为每安装仅保留最新一条样本，升级时删除更早历史并建立 `device_id` 唯一索引。schema 8 增加全网模型收益基线、间隔汇总与切换记录表。schema 9 为全网间隔增加范围、忙碌 Provider 与单 Provider 最大 token。schema 10 为 `provider_id` 为空的奖励明细补哨兵值 `bloomer_reward`，使按设备归属的分析查询能看到这类账户级收入。数据库默认位于用户应用数据目录，不进入仓库。

## 表和连接

- `earnings`：`(account_id, record_id)` 主键，保留来源文本 ID；时间与模型查询各有组合索引。金额为有符号 int64 微美元，时间为 UTC 整数微秒。上游对奖励明细不填 `provider_id`，落库时改写为哨兵值 `bloomer_reward`（仅限空白 Provider 的奖励行，其他行保持原值），读取明细时再还原为空字符串，避免这条自定义值出现在接口与 CSV 中。
- `account_summary_current`：每个账户仅保留最新官方汇总，不每分钟永久追加快照。
- `sync_state`：最近尝试、完整成功、错误分类、同步模式、覆盖状态与上次写入计数。
- `coverage_gaps`：观测中断及疑似缺口，带账户和时间索引；不等同于精确丢失收益边界。
- `maintenance_state`：单行启动、正常关闭、清理成功和限流截止时间；schema 2 增加绑定账户、最近尝试/错误/恢复原因、时钟高水位、持久化清理截止时间、最近清理尝试及错误。首次成功事务绑定账户；已有单账户历史在读取时推断，多账户库拒绝作为本服务运行。
- `schema_migrations`：版本、文件名、SHA-256 与迁移时间；与 `PRAGMA user_version` 共同检查。
- `device_identity`：本安装持久标识与最近成功读取的固定硬件信息；不声称等于官方 Provider 身份。
- `device_state_samples`：每 60 秒覆盖保存本安装最新一条设备资源和 Provider 观察；指标是可空的明确列，`quality_json` 区分未知与零值。不参与收益 365 天清理。详见[设备状态采集](device-state.md)。

SQLite 使用 WAL、FULL 同步、5000 ms 忙等待和外键检查。写连接最多 1 个，只读池最多 2 个；配置通过 DSN 应用于每个连接。只读连接使用 `mode=ro` 和 `query_only=1`。所有写操作经存储模块的串行事务入口；P2/P3 使用同一任务协调器，采集全轮与清理批次之间互斥，网络阶段不持有 SQL 事务。另建 `earnings_retention_time(created_at_us)` 索引支持过期分批删除。

P2 整轮合并后原子提交明细、最新官方快照、覆盖与成功时间。内容未变化的明细不执行 UPDATE；部分扩窗失败丢弃整轮缓冲。网络请求不得放在写事务内。数据库不可用时返回明确错误，不能将错误转换为 0 收益。

## 迁移

1. 服务获取数据目录的 OS 文件锁。
2. 检查 `user_version`、迁移历史与已应用文件的校验和。
3. 新建空库直接初始化；不接管未版本化的非空库。高于当前程序支持的 schema 拒绝启动。
4. 已有版本升级前，通过 `VACUUM INTO` 创建包含已提交 WAL 数据的一致性副本；文件名为 `agent.db.pre-v<目标版本>-<纳秒时间>.bak`。
5. 每个 SQL 文件在短事务内执行；SQL、迁移历史和版本号一起提交。失败时整份文件回滚并停止启动，已完成的较早版本仍保持有效。

已应用的迁移文件不可修改；新增结构使用下一个连续编号。迁移的“可回滚”指**失败迁移的事务回滚**与一致备份恢复，不提供破坏性在线 down migration。测试覆盖初次失败无残留、旧版升级失败、DDL 回滚、重新升级、高版本拒绝和校验和冲突。

## 一致备份与恢复

存储模块已提供经写锁协调的 `VACUUM INTO` 备份能力，并验证主库/WAL 中的数据和维护检查点恢复一致；当前尚未开放备份 CLI。升级会自动调用该能力。不要在服务写入时只复制 `.db` 主文件。

需要恢复数据库时：

1. 正常停止 Agent 并确认进程已退出；尚未安装 launchd 时，使用终端 Ctrl+C 或 SIGTERM。
2. 将现有 `.db`、`-wal`、`-shm` 作为同一组保存在单独故障排查目录。
3. 将一致性备份复制为配置指定的 `agent.db`，不要混入旧 WAL/SHM。
4. 保持数据目录 0700、数据库 0600，使用支持该 schema 的程序重新启动，核对健康与检查点。
5. 验证升级成功后按需移走或删除升级前临时备份；当前不自动删除恢复保障文件，也不默认周期备份。

启动、停止和迁移的日志可用于核验。正常退出记录失败时程序报告错误；强制退出不会伪造正常关闭时间。P3 每轮以最近成功时间判断 30 分钟恢复，时钟异常采用恢复读取；每周清理按 1000 条短事务推进，冻结的清理截止时间跨重启保留，只有最后一批成功才推进清理成功时间。清理失败至少间隔 60 秒重试，不执行全库 VACUUM。查询基础方法对明细与合计共用当前 365 天过滤，早于保留期的显式查询返回截断标记和可用起点；正式 HTTP 查询在 P4 实现。
